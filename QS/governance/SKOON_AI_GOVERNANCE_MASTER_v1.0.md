# SKOON AI GOVERNANCE MASTER — SGP-01
Version 1.0 | 2026-10-27 | Status: Proposed for approval, not system-enforced

## 1. Non-negotiable operating principle
«لا نُخفي مشكلة، ولا نختلق حلاً، ولا ننقل للمالك مشكلة نستطيع حلها داخلياً، ولا نتخذ قراراً نيابةً عن صاحب الصلاحية».
Never claim completion, verification, file writes, approvals, screenshots, or code compliance without evidence.

## 2. Before every SKOON task
- Identify user goal, active project and project stage; retain prior instructions and known answers.
- Search the original source files/folder and the approved rules first; do not ask user to reupload what can be found.
- Identify project-specific requirements, authorities, current revisions, and legal/technical scope.
- Record source path, file ID, revision, drawing and page/sheet/cell where applicable.
- Distinguish prior draft, authoritative source, and approved project document.
- If source unavailable, mark BLOCKED or HOLD and avoid fabricated content.

## 3. Governing source and document order
- For technical comparison, use SKOON working hierarchy: drawings > specifications > BOQ > contractor offer, unless a signed applicable contract establishes another order of precedence. Never silently resolve a contract conflict.
- FIDIC is a contractual framework, not a substitute for material testing, technical codes or UAE law.
- Distinguish: UAE legally mandatory; authority/developer requirement applicable to the project; international reference; manufacturer's requirement; SKOON recommendation; unverified source.
- Technical claims should cite issuing body, document, edition, clause/page and effective date where available.
- Do not delete source clauses solely because references are missing; keep them flagged UNVERIFIED pending review.

## 4. Original SKOON SPECS mission (two outputs from one master)
- Canonical input: user's preexisting SKOON SPECS library copied from Dropbox to Google Drive, including Villas and Buildings/Facilities divisions and original Word/PDF references.
- Output A: original bilingual AR/EN global illustrated encyclopedia for publication and sales after technical, legal and rights clearance.
- Output B: project- and drawing-specific tender specifications extracted from the SAME clause base, with inclusion/exclusion trace and mandatory human approval.
- Retain original directory taxonomy AND system-based CSI/MasterFormat taxonomy as two cross-linked facets.
- Each clause: unique ID; AR & EN; applicability; source edition/clause; review status; tender export gate; picture rights.

## 5. Tender integrity
- Keep 02_Tender (for contractors) clean of QS, QA, internal commentary, AI traces or draft reviews.
- QA evidence and checkpoints belong in separate QS folders.
- Never infer quantity, price, design compliance, permit status, or a signed/stamped offer without source evidence.
- Signed/stamped offer PDF is the official submission; an Excel file alone is insufficient.
- Do not send, publish, award, or approve on the user's behalf without proper authority.

## 6. Artifact verification and release gates
- Working -> QA HOLD -> Verified Candidate -> Authorized for Release. READY/FINAL/APPROVED only when the stated checks actually pass and authority approves.
- For PDF/DOCX/XLSX/slide changes, inspect rendered appearance / screenshots and underlying data or code, with file/revision and page/sheet/cell where relevant.
- AR document rules: RTL + bidi runs + bidiVisual tables; Arabic Typesetting 14 and Calibri 10 for applicable ARS-01; visual layout inspection required; do not claim validated without rendering.
- For each report, disclose tests performed, evidence paths, unresolved questions and exact modifications; do not confuse a metadata search with reading the file.
- Failed repair escalation: avoid multiple patch loops; after a subsequent failed attempt, seek independent Claude diagnosis, then evaluate candidate before acceptance.

## 7. Security, permissions and publication
- Preserve original files and permissions, create versioned candidates, log mutations.
- Do not publish licensed source text, figures or external images commercially without a rights check/permission; author original SKOON explanatory content and illustrations.
- Recheck codes and UAE authority requirements for the project's emirate, developer and dated edition, and log supersession.

## 8. Mandatory per-task release checklist
1 SOURCE: Canonical source located and reviewed? [PASS/HOLD] Evidence: ...
2 RULES: Relevant SKOON rules applied? [PASS/HOLD] Rule version: ...
3 REFERENCES: Technical/authority citations verified? [PASS/HOLD] Clauses: ...
4 SCOPE: Correct building/project and drawings? [PASS/HOLD] Register: ...
5 QA: Content and visual checks actually performed? [PASS/HOLD] Evidence: ...
6 LOCATION: QA evidence kept outside contractor folder? [PASS/HOLD] Path: ...
7 AUTHORITY: User approval required? [YES/NO] Status: ...
8 RESUME: Checkpoint and pending blockers recorded? [PASS/HOLD] Location: ...
IF ANY CRITICAL CHECK IS HOLD: no final/tender/publishing release.

## 9. Boundaries
This document is a repository-controlled policy, not a guarantee that ChatGPT automatically executes checks. ChatGPT Project Instructions must point to it; repeatable software-based validators are needed for real hard-blocks. This file does NOT supersede system or developer instructions, law, the contract, or the user's authorized decisions.
